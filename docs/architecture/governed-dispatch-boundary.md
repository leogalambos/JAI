# Execution and effect boundaries

The native parent delegates professional work through the active provider and
uses the shared runtime to bind an issued assignment, context and actual return.
A declared role or claimed actor name alone is not execution provenance.

## Task-specific input

Each entity receives the exact assignment, relevant input sections, criteria
and supporting references for its work. Author and reviewer contexts remain
separate. A filesystem path alone does not establish an immutable source
identity or entitlement to modify its meaning.

The complete role and workflow catalogue is an intrinsic professional resource,
not input that a neighbouring layer may withhold to control staffing. Project
requirements and handoff material remain versioned inputs supplied through the
declared interfaces.

## Permitted effects

Professional tool tiers and the effective provider sandbox bound available
operations. A read-only reviewer does not gain write permission through a role
description, a returned JSON object or a request from another layer.

The host sandbox enforces filesystem and process permissions. Behavioural
instructions and managed hooks complement that boundary; they do not provide
universal operating-system isolation or enterprise identity management.

## Results and human authority

The runtime admits actual captured returns against the issued work. Completion
is distinct from a positive professional review, output acceptance and release.
Cancelled or stale work cannot silently regain applicability because its process
eventually returned a result.

Reserved human decisions use the [external signing procedure](../operations/human-authority.md).
Private keys remain outside entity sandboxes; the runtime verifies public proof
and exact effects. Signing does not expand sandbox permissions.
